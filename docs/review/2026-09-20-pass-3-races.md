# Pass 3: Races, idempotency and transactions

Reviewed 2026-09-20 against `main` at 9775408. Read-only. Files read: `db/index.ts`, all 27 `db.transaction` call sites (scanned each body for queries that escape to the non-transaction client: none found), `lib/cron/handler.ts`, `actions/admin-settings.ts` (run now), `actions/session-requests.ts`, `lib/session-requests/accept.ts`, `db/queries/session-requests.ts`, `db/queries/sessions.ts`, `db/queries/broadcasts.ts`, `actions/bookings.ts`, the overlap constraint in `drizzle/0001` and `0013`, and the lock order across settlement, force-cancel, refund reversal, release-earnings and withdrawals.

What held up: the two-client setup is wired correctly. `db.transaction` is bound to `transactionClient`, every transaction body uses its `tx` handle only, and savepoints go through `tx.transaction`. No transaction runs on the no-pipelining client and no plain query runs inside a transaction. Every cron route goes through `cronAuthFailure`, which returns 503 when `CRON_SECRET` is unset and 401 on a mismatch. "Run now" calls the job function directly behind `requireRole('admin')`. Session end, earnings release, withdrawal transitions, booking confirm and request accept are all conditional UPDATEs or lock-then-check, in that order. Two bookings cannot take one slot (`bookings_no_overlap` counts `pending_payment`, `confirmed`, `in_progress`). One live broadcast per tutor is a unique index. I looked for a lock-order cycle between settlement (payment, wallet, booking), force-cancel (booking, student wallet, earnings, tutor wallet), release (earnings, tutor wallet) and withdrawals (wallet, request / request, earnings) and did not find one.

## Confirmed by reading

### R1. "One pending request per student" is check-then-insert with no database guard. MEDIUM
- `src/actions/session-requests.ts:162-168` and `:185`; schema `src/db/schema/booking.ts:94-95` (two plain indexes, no partial unique index).
- Sequence: a student with 100 credits sends two requests at the same moment (two tabs, or a double submit) to tutors A and B at 40 credits each. Both calls run `getPendingRequestForStudent` before either inserts, both see nothing, both insert. The balance check is per request (`balance < priceCredits`), so both pass. A and B both accept: two `booking_debit` rows land (the wallet lock serialises them and 80 is covered), the student is in two paid sessions at once and SPEC 7.4 refunds nothing. If the balance only covers one, the second tutor's accept ends `failed_payment` after they committed to it.
- Withdrawals solved the same shape with `withdrawal_requests_one_open_per_tutor`. There is no equivalent here.

### R2. Completion and earnings are separate commits. MEDIUM
- Recorded as M2 in pass 1 (`src/lib/sessions/complete-sessions.ts:69-130`). Listed here because it is the one place in the money path where "work that should be in one transaction" is not: status flips auto-commit, the earnings insert follows from memory, and a death in between is permanent because the rows have left every work set. Admin force-complete does it correctly (`db/queries/admin-bookings.ts:400-460`, one transaction), so the two paths disagree.

### R3. Unpaid holds are free and uncapped. LOW
- `src/actions/bookings.ts:126-171`.
- Choosing PayPal inserts a `pending_payment` booking that blocks the slot for 20 minutes with no debit. Nothing limits how many a student may hold or how often they may re-create them. One verified student account can block every open slot on a tutor's calendar and renew the holds every 20 minutes. No money moves, but the tutor is unbookable.

### R4. The accept path compares the deadline on the app server's clock. LOW
- `src/lib/session-requests/accept.ts:171-175`. `expires_at` is written by Postgres (`now() + interval`) precisely so every reader uses one clock (SPEC 7.4), but accept compares it with `new Date()` from the Vercel instance. Clock skew of a second or two either way decides whether a last-moment accept charges the student. The end-session path does this properly in SQL.

### R5. Accept-time collision check ignores `pending_payment` and is an unlocked read. LOW
- `src/db/queries/session-requests.ts:32` and `:418`. `OCCUPYING_STATUSES` is `confirmed` and `in_progress`. A scheduled booking sitting in `pending_payment` for a slot ten minutes from now does not block a 60-minute instant accept; the capture then confirms it and the tutor is double-booked. The read is also not serialised against `createScheduledBooking`, so a booking inserted between the read and the commit has the same result. SPEC calls it a guarded read, not a constraint, so this is by design, but the `pending_payment` omission is not discussed anywhere.

## Suspicions, not verified

### R6. Cron work under a function time limit.
- `release-earnings` runs one transaction per due row in a loop, and `complete-sessions` one statement per elapsed instant session plus two bulk updates. Neither cron route sets `maxDuration` (the Agora token route does, at 60). On a large backlog the run could be cut off. For `release-earnings` that is safe (rows stay `held`). For `complete-sessions` a cut-off between the sweeps and the insert is R2. I did not check the Vercel plan's default limit.
