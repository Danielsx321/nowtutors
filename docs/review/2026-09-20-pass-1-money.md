What held up: no code path outside `lib/credits/ledger.ts` writes `wallets` or `credit_transactions` (grep for every insert/update/delete form, only `db/seed.ts` besides the ledger). ## Confirmed by reading

### M1. A tutor is never paid for an instant session that a participant (or the deadline actor) ends. HIGH
- `src/lib/sessions/complete-sessions.ts:69-81` and `:130`; `src/db/queries/complete-sessions.ts:108-123`; `src/actions/sessions.ts:108` and `:170`; `src/app/api/agora/token/route.ts:103`.
- `complete-sessions` is the only writer of `tutor_earnings` apart from admin force-complete, and it builds earnings rows only from the bookings it transitioned itself in that run (`swept`). Its instant work list is `status = 'in_progress'`.
- Three other actors move an instant booking to `completed` and write no earnings row: `endSession` (early exit), `getSessionState` (the actor at the deadline when people are still in the room, which its own comment calls the common case), and the token route's deadline branch.
- Sequence: tutor accepts, student is debited 40 credits, both stay in the room, the countdown hits zero, the client calls `getSessionState`, `endElapsedInstantSession` sets `completed`. Next cron run: `findElapsedInstantSessionIds` does not return the row (it is no longer `in_progress`), so `swept` never contains it and no `tutor_earnings` row is ever inserted. `release-earnings` has nothing to release. The student paid 40, the tutor's wallet gets 0, permanently.
- No recovery in the app: `canForceComplete` refuses a booking that is already `completed`. Only a manual SQL insert fixes a row.
- Only sessions that end with nobody present (cron closes them) or no-show classifications get an earnings row today.
- Confidence: high. Verified there is no fourth step in `runCompleteSessionsSweep` and no other caller of `insertHeldEarnings` (grep: only `complete-sessions.ts:130` and `admin-bookings.ts:438`).

### M2. The completion sweep commits status changes before it writes earnings, outside any transaction. MEDIUM
- `src/lib/sessions/complete-sessions.ts:69-130`.
- The three sweeps are auto-committed UPDATEs. `insertHeldEarnings` runs afterwards from memory. If the function dies in between (Vercel timeout, a failed `insertHeldEarnings`, a deploy), the bookings are already `completed` or `no_show_student`, have left every work set, and get no earnings row on any later run. Same permanent outcome as M1, for scheduled sessions too.
- The `ON CONFLICT DO NOTHING` the comments rely on protects against paying twice. Nothing protects against paying zero times.
- Second consequence: an admin force-cancel landing in that window sees no earnings row (`tutorReversal = none`), refunds the student, and the sweep then inserts a `held` row for the cancelled booking, which `release-earnings` will pay.
- Confidence: high on the mechanism, the window is short per run.

### M3. First-ever credit to a wallet can lose an update under concurrency. LOW
- `src/lib/credits/ledger.ts:127-134` and `:214-219`.
- Wallet rows are created lazily (no signup trigger, no migration inserts them). When `lockWallet` returns null there is no row to lock; `createWallet` inserts with `ON CONFLICT DO NOTHING` and the code continues with `current = 0` without re-locking or re-reading.
- Sequence: two transactions make a user's first two credits at once with different references (for example `release-earnings` for a new tutor running from pg_cron and from the admin "run now" button, each on a different booking; or a first purchase racing an admin adjustment). A inserts the wallet row, appends +10, sets balance 10, commits. B's insert waited on A's uncommitted row, now does nothing, still believes `current = 0`, appends +5 with `balance_after = 5`, sets balance 5. Ledger sum 15, cached balance 5, and B's `balance_after` is wrong in an append-only table.
- `reconcile-wallets` would flag it the next night. Confidence: high on the mechanism.

### M4. A late `PAYMENT.CAPTURE.COMPLETED` still mints credits for a payment already marked refunded. LOW
- `src/lib/paypal/settlement.ts:162-170`, then `:231-250` and `:302-313`.
- The `refunded` guard only skips the status update. The mint below it is unconditional.
- Sequence: buyer approves, closes the tab, the COMPLETED webhook fails (503 while `PAYPAL_WEBHOOK_ID` was unset, or a DB blip) and is queued for retry; the payment is refunded in PayPal, REFUNDED arrives and marks the row `refunded`; PayPal retries COMPLETED; `settleCapture` leaves the status alone and credits the wallet in full.
- Confidence: high on the code, depends on webhook ordering.

### M5. The webhook cannot tell a partial refund from a full one. MEDIUM
- `src/lib/paypal/webhook.ts:224-228`, `src/lib/paypal/settlement.ts:331-345`, `src/db/queries/admin-bookings.ts:474-560`.
- PayPal sends `PAYMENT.CAPTURE.REFUNDED` for partial refunds as well. The handler never reads the refund amount, so any refund marks the payment `refunded`. SPEC 7.6 assumes that status means a full refund.
- Sequence: admin refunds $5 of a $50 package in PayPal as goodwill. Payment shows `refunded`. "Reverse this refund" then removes all the minted credits (up to the balance), or for a direct-pay with a standing debit, cancels the whole booking with no credit refund and reverses the tutor's earnings.
- Confidence: high on the code; PayPal's partial-refund event behaviour is from their docs, not tested here.

### M6. Direct-pay can mint and debit a different amount than `bookings.price_credits`. LOW
- `src/lib/paypal/direct-pay.ts:52-57`, `src/actions/bookings.ts:122` and `:160`, `src/lib/sessions/complete-sessions.ts:113`.
- The booking pins `price_credits` at creation. The order route re-derives from the tutor's current rate, by design (SPEC 7.6 says so). Earnings are later split from `bookings.price_credits`.
- Sequence: booking created at rate 40 (`price_credits = 40`, `pending_payment`). Tutor raises the rate to 60 within the 20-minute hold. Student opens PayPal: order, mint and `booking_debit` are 60. Tutor's earnings are split from 40. The student paid 20 credits more than the booking records and the platform keeps the difference. With a lowered rate the platform pays the tutor from more than the student paid.
- The instant path does the opposite on purpose (charges the pinned quote). Confidence: high.

### M7. `platform_fee_percent = 100` strands every earnings row. LOW
- `src/lib/settings-schema.ts:82-87`, `src/lib/credits/ledger.ts:123`, `src/lib/earnings/release-earnings.ts:126`.
- The setting accepts 100. `net_credits` becomes 0, `creditWallet` throws on a zero delta, the row rolls back to `held` and lands in `failedIds` every hour forever. Any fee that makes net 0 on a 1-credit session does the same.

## Suspicions, not verified by reading alone

### M8. Webhook signature check re-serialises the event.
- `src/app/api/webhooks/paypal/route.ts:40-45`, `src/lib/paypal/webhook.ts:53-67`.
- The verify call sends `JSON.parse(rawBody)` back through `JSON.stringify`. PayPal's verification is sensitive to the exact event bytes; re-serialising changes whitespace, unicode escapes and number formatting. If a payload carries a non-ASCII payer name or an escaped character, verification may fail, the route answers 400, and the backstop is dead for that buyer while PayPal retries for days. Needs a sandbox test with a non-ASCII buyer name.

### M9. A tutor can accept a second instant request while already in a session.
- `src/lib/session-requests/accept.ts:185-190`, `src/db/queries/session-requests.ts:418`.
- The accept-time collision check reads scheduled bookings only. Nothing reads the tutor's own `in_progress` instant booking, and `live_tutors` has no in-session exclusion. If the tutor still shows as live during a session, student B can request, the tutor (second tab, or the incoming modal) accepts, and B is debited in full for a session the tutor cannot give. There are no refunds. SPEC 7.4 is silent on it. Whether the tutor stays in `live_tutors` while in `/session` needs a runtime check.

### M10. `PAYMENT.CAPTURE.REVERSED` (chargebacks) is not handled.
- `src/lib/paypal/webhook.ts:79-83`. Per SPEC, which lists three events. A disputed and reversed capture leaves the payment `captured` and the credits spendable, with no signal on `/admin/payments`.

### M11. Order row can be orphaned between insert and stamp.
- `src/app/api/paypal/orders/route.ts:107-157`. If the process dies after `createPayPalOrder` returns and before the `provider_order_id` update, the row keeps `pending:<id>`. The buyer can still approve; the capture route 404s and the webhook reports `unknown_order` with a 200. `custom_id` carries our payment id but nothing looks a payment up by it. Money taken, no credits, no retry.

### M12. Earnings can stay `available` after the withdrawal that paid them.
- `src/db/queries/withdrawals.ts:126-145`. `markEarningsWithdrawn` compares `credit_transactions.created_at` with the request's `created_at`. Both are transaction start times. A request transaction that starts first but takes the wallet lock after a release commits will sweep those credits into its amount while the release row's timestamp is later than the request's, so the row is left `available`. A later force-cancel of that booking would then try `debit_available` against credits from other sessions. Millisecond window.
